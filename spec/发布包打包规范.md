# 发布包打包规范（WinClaw 自动更新）

> 本文件是 **WinClaw 自动更新发布包** 的唯一权威打包准则。
> 之后的 WinClaw 对话 LLM / 开发助手在"打包 / 打发布包 / 发布版本 / 生成安装包"时，
> 必须先读本文件并**严格遵循**。人类运维同守。

**适用对象**：所有通过自动更新分发（服务器 `10.233.129.67`）发布的 WinClaw 桌面端版本。

---

## 1. 发布包由两个文件构成

| 文件 | 说明 |
|------|------|
| `Hs-WinClaw-Setup-<版本>.exe` | Inno Setup 安装包（`build_installer.bat` 产物） |
| `winclaw-update.json` | 更新清单（客户端实际拉取判断版本/校验哈希/展示说明） |

产物统一落在仓库 `installer/` 目录。

## 2. 命名规范（强制）

- 安装包文件名：**必须**是 `Hs-WinClaw-Setup-<版本>.exe`，例如 `Hs-WinClaw-Setup-1.4.2.exe`。
- 更新管理端（8081）只认可该命名——裸 `.exe` 上传时靠文件名推断版本号，写错就没法识别。
- 若要打成 zip 交付给管理端上传，zip 内直接放上述 exe + `winclaw-update.json` 两个文件。

> ⚠️ **严禁**产出 `Hs-WinClaw-Setup-<版本>-update-package.zip` 这类"文件名 + 裸 exe"的伪 zip。
> 它根本不是 zip（开头是文件名文本，真正的 PK 压缩头在偏移 512 处），管理端/任何 zip 工具都会解析失败。
> 2026-08-20 已踩坑：上传 `Hs-WinClaw-Setup-1.4.2-update-package.zip` → 「zip 解析失败：不是有效的 zip 文件」。

## 3. zip 打包的正确方式

标准 zip 的特征 = 文件首 4 字节 `PK\x03\x04`（`50 4B 03 04`）。生成方式二选一：

```powershell
# 方式 A：PowerShell（Windows 自带）
Compress-Archive -Path install_dir\Hs-WinClaw-Setup-<版本>.exe, install_dir\winclaw-update.json `
                 -DestinationPath installer\WinClaw-<版本>-发布包.zip -CompressionLevel Optimal
# 方式 B：7-Zip 命令行
7z a "installer\WinClaw-<版本>-发布包.zip" "installer\Hs-WinClaw-Setup-<版本>.exe" "installer\winclaw-update.json"
```

打包后先自检：`xxd -l 4`（或记事本/压缩软件打开）确认是 zip，不是别的东西。

## 4. 清单字段要求（winclaw-update.json）

```json
{
  "version": "1.4.2",
  "url": "http://10.233.129.67:8080/update/Hs-WinClaw-Setup-1.4.2.exe",
  "sha256": "与 exe 实际哈希一致（小写 hex）",
  "notes": "- 每条更新说明一行，客户端更新弹窗原样展示",
  "mandatory": false,
  "publishedAt": "2026-08-20"
}
```

- `url` 前缀**必须**是 `http://10.233.129.67:8080/update`（更新服务器，知识库 web 登录同址）。
  历史上曾误写 `10.233.129.65`（Git 服务器）导致客户端 404，已在源码 `tools/gen_update_manifest.ps1` 默认 BaseUrl 和
  `src/HsWinClaw.Desktop/appsettings.json` 中修复为 `.67`。
- `sha256` 必须 = 对应 exe 的 SHA-256（小写），否则客户端校验失败会中止更新。
- `notes` 建议直接取 git 提交历史（`tools/gen_update_manifest.ps1` 自动生成）。

## 5. 出包流程（优先走构建脚本，不做手工）

1. 构建安装包：运行仓库根 `build_installer.bat` → 产出 `installer\Hs-WinClaw-Setup-<版本>.exe`。
2. 生成清单：构建脚本自动调用 `tools\gen_update_manifest.ps1 -RepoRoot <仓库> -Version <版本>`
   （自动算 SHA256、写 `.67` 的 url、从 git 日志生成 notes）→ `installer\winclaw-update.json`。
3. 清点产物：确认 `installer\` 下 exe + json 齐全、版本号一致、清单 sha256 = exe 哈希。
4. 如需整包上传：按第 3 节打成**标准 zip**。

## 6. 发布 / 回滚（更新管理端）

- 管理地址：`http://10.233.129.67:8091`（端口 8091，非 8081；宿主机 8081 被其他服务占用）。
- 上传：拖拽标准 zip；或直接传裸 `Hs-WinClaw-Setup-<版本>.exe`（自动按文件名推版本）。同名版本重复上传会报冲突，需先删除旧包。
- **设为发布**：列表里点目标版本「设为发布」→ 服务端原子写 `winclaw-update.json` → 客户端在 24h 检查周期内自动更新。
- **回滚**：把旧版本重新「设为发布」即可，客户端回到旧包。
- **删除**：只能删非当前发布版本；当前发布版本被保护（需先发布别的版本）。
- 发布说明编辑：列表「编辑说明」→ 若该版本是当前发布，会同步刷新客户端清单的 notes。

## 7. 上传前自检清单（发布者逐项确认）

- [ ] exe 文件名 = `Hs-WinClaw-Setup-<版本>.exe`
- [ ] zip（若用）= 标准 zip（PK 头），内含 exe + winclaw-update.json
- [ ] `winclaw-update.json` 的 version 与 exe 版本一致
- [ ] url = `http://10.233.129.67:8080/update/...`（`.67`，不是 `.65`）
- [ ] sha256 = exe 实际哈希（可 `certutil -hashfile Hs-WinClaw-Setup-<版本>.exe SHA256` 核对）
- [ ] 上传管理端后，`curl http://10.233.129.67:8080/update/winclaw-update.json` 返回新版本号
- [ ] 无把测试/半成品包留在当前发布位置；测完用旧版本重发布恢复

## 8. 关键约束速查（易错点）

- 更新服务器 = `10.233.129.67:8080`（`.67`）；Git 服务器 = `10.233.129.65:8800`（不要混用）。
- 管理端端口 = `8091`（`8081` 已被宿主机 python 服务占用）。
- 伪 zip（`-update-package.zip`）禁止作为上传交付物。
- 已发布的旧安装包若内置过 `.65`，需靠新版本覆盖升级或手动改安装目录 `appsettings.json`。
